# Resona — full app audit (2026-11-20)

Scope: the Electron shell (`desktop/`), the Tauri shell (`desktop-tauri/`), the
Next.js server (`src/lib/server/**`, `src/app/api/**`), the renderer/player
(`src/lib/player-engine.ts`, `src/stores/**`, `src/components/**`), the update
pipeline (electron-updater + the GitHub release flow) and CI (`.github/workflows/`).
Every finding was verified against the actual code — nothing speculative.

Legend: **FIXED** — code changed in this pass. **FLAGGED** — real issue, fix
specified below, not yet applied. Severity: CRIT / HIGH / MED / LOW.

---

## 1. The update bug — "the app opens right after updating but doesn't receive the update"

### Root cause (three stacked defects, all FIXED)

1. **The startup-update path was dead code.** `desktop/main.js` capped the
   boot-time update at `UPDATE_WAIT_MS = 10000` (10 s), but the Windows
   installer is ~150–250 MB. On any realistic connection the download never
   finished in 10 s, so the `quitAndInstall(true, true)` path — the only one
   that installs *and* relaunches — practically never ran. Result: the splash
   said "Downloading update…", hit the cap, and **the app opened on the old
   version** ("opens right after when updating").
2. **The fallback path never relaunches.** With the startup path dead, every
   update landed in `autoInstallOnAppQuit`, which electron-updater 6.8.11 runs
   as `install(true, false)` → NSIS gets `--updated /S` with **no
   `--force-run`** → files are replaced while the app is closed, but the app is
   **never relaunched** and nothing tells the user. That is "the app isn't
   receiving the update, it should restart first".
3. **The relaunch race corrupted updates.** If the user relaunched the app
   while that silent installer was still running, the installer's
   `_CHECK_APP_RUNNING` kills by image name (`taskkill /f /im Resona.exe`) —
   it cannot tell the *fresh* instance from the leftover one, so the new
   launch got force-killed (app flashes open then gone), or the installer
   aborted leaving a **partially copied install dir** — the literal
   "installed, but opens old/mixed version" outcome.

### The fix (desktop/main.js, desktop/preload.js, src/components/UpdateBanner.tsx)

- `UPDATE_WAIT_MS` 10 s → **30 s** (progress shows on the splash). A download
  that lands while the splash is up now **installs immediately and the
  installer relaunches straight into the new version** — the app never opens
  on a stale build.
- A download that lands **while the app is running** no longer silently
  defers: the main process pushes `update:ready` over IPC and a green
  **"Update ready — Restart now"** banner (UpdateBanner.tsx, mounted in
  AppShell) offers a one-click install+restart. "Later" dismisses; the quit
  path still applies it silently as a last resort.
- New `installAndRestart()` sequence: stop the server child first (it is also
  `Resona.exe` under `ELECTRON_RUN_AS_NODE` and must not die mid-write or race
  the installer), destroy windows, `quitAndInstall(true, true)` (silent +
  force-run), then a hard `app.exit(0)` fallback after 5 s so a stalled quit
  can never wedge the handover.
- Updater listener hygiene: the one-shot `update-not-available`/`error`
  handlers are removed when the startup check finishes instead of lingering
  for the process lifetime.

**Answer to "why does the app open right after when updating":** it opened on
the old version because the only install+relaunch path was capped at 10 s
(dead code) and the real path installed silently without ever restarting. Now
the app restarts *through* the update: splash → download → quit → installer
replaces files → relaunch into the new version.

## 2. Electron / desktop shell

- FIXED — update flow (see §1).
- FLAGGED (MED) — **version lives in 5 unsynced places** (`package.json`,
  `desktop/package.json`, `src/lib/version.ts`, `tauri.conf.json`,
  `Cargo.toml`). The renderer's update banner compares root `package.json`
  while electron-updater compares `desktop/package.json`; a drift produces a
  false "up to date". Fix: derive both at build time from one source, or add a
  CI assertion (the existing version.test.ts guard covers only two of the five).
- FLAGGED (MED) — **release pipeline is fully manual**: desktop.yml builds
  artifacts with `--publish never`; `latest.yml` reaching the release page is
  a convention guarded by a shell script with hard-coded IDs. Any skipped step
  silently breaks auto-update (electron-updater's logger is null). Fix: a
  publish job that uploads `Resona-Setup-*.exe + .blockmap + latest.yml` in
  the same build that produced them.
- FLAGGED (LOW) — the server child is killed with `TerminateProcess`
  (`serverProc.kill()` on Windows); a graceful shutdown request to the server
  before kill would let SQLite finish writes (WAL journaling already makes
  this survivable).
- FLAGGED (LOW) — legacy `desktop/installer.nsi` is a footgun: hardcoded
  version 1.0.0, "MIT License" on a GPL-3.0 project, no running-app check,
  output name collides with electron-builder's artifact. Not referenced by
  electron-builder (the build uses the `nsis` target in desktop/package.json).
  Recommend deleting it.

## 3. Tauri shell (desktop-tauri/) — was dead on arrival in release builds

- FIXED (CRIT) — **no capabilities file existed**, so Tauri 2's ACL denied
  every IPC call: the splash's `invoke("server_url")` always rejected ("Resona
  could not start its music server") and the window controls were dead. Added
  `src-tauri/capabilities/default.json` (core:default + the five app command
  permissions, for the `main` window, local **and** remote
  `http://127.0.0.1:*` context — the app page is remote, splash-only local
  would not cover it). CI verifies: a wrong identifier fails the build.
- FIXED (CRIT) — **wrong sidecar path**: `node_path()` looked in
  `binaries/node.exe`, but the bundler installs `externalBin` targets flat
  next to the exe (`$INSTDIR\node.exe`) — the server could never spawn from
  the NSIS/deb build. Now the flat location is checked first, `binaries/`
  stays as the dev fallback.
- FLAGGED (HIGH) — **no updater in the Tauri shell** (no
  `tauri-plugin-updater`, no signing keys, no `createUpdaterArtifacts`):
  Tauri users must reinstall manually every release. Fix: add the updater +
  process plugins and signed updater artifacts in CI, or document Tauri as
  manual-install-only.
- FLAGGED (MED) — no `tauri-plugin-single-instance`: two Tauri instances can
  write one SQLite DB (Electron has `requestSingleInstanceLock`).
- FLAGGED (MED) — sidecar kill covers graceful exit only; a crash/TerminateProcess
  orphans `node.exe` holding the DB and port. Fix: Windows Job Object with
  `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`.
- FLAGGED (MED) — `csp: null` + `withGlobalTauri` injects `__TAURI__` into the
  remote page: any script running in the served app could call the (small)
  IPC surface. Set a CSP for the splash at minimum.

## 4. Server (src/lib/server/**, src/app/api/**)

- FIXED (HIGH) — **non-atomic `replaceLibrary` could silently wipe history
  (or the whole library) while returning ok**. The restore deleted all four
  tables then inserted; a duplicate `videoId` in a backup's history (the
  single multi-row INSERT hits the PK) or a crash mid-restore left the library
  half-wiped. Now: one drizzle transaction (`db.transaction`), history deduped
  by videoId (newest kept, capped at HISTORY_LIMIT), playlists deduped by id,
  likes/history inserted in 500-row chunks, playlist tracks capped at 2000.
- FIXED (HIGH) — **SSRF through the `/api/stream` chain**: the `instances`
  param and the instance-returned stream URLs were used verbatim by the byte
  proxy. Now `isSafeStreamUrl()` (instance-fleet.ts) gates every URL that
  comes back from a Piped/Invidious instance — https only, no loopback /
  private / link-local hosts — and `parseInstanceSetting` is bounded
  (max 6 instances, ≤200 chars each). Covered by new unit tests.
- FIXED (MED) — **`cached()` never served stored `null`s**: kworb's cached
  "unresolvable trending row" was recomputed (two YT Music searches) on every
  request forever. `cached()` now uses the same entry lookup as `cacheGet`,
  so cached nulls are honored for their TTL.
- FIXED (MED) — **unbounded cache growth**: expired `kv` rows were deleted
  only once at boot. An hourly pruner (unref'd interval) now clears expired
  rows in the DB and in both in-memory layers.
- FIXED (MED) — **`proxyFetch` had no deadline**: a stalled upstream held the
  route open up to undici's ~300 s inactivity default. Now a 15 s headers
  deadline (body has none — songs legitimately stream for minutes).
- FIXED (LOW) — non-transactional `putPlaylist` (delete committed before a
  possibly-failing insert) is now transactional with the same track cap.
- FLAGGED (MED) — LRCLIB fan-out can take tens of seconds on a cold
  no-lyrics track (up to ~9 title variants × 3 get + ~18–27 search calls,
  serial, 10 s timeouts each). Fix: cap attempts and run variants in small
  parallel batches.
- FLAGGED (MED) — `/api/durations` worst case ~3 minutes (60 ids × 12 s at
  concurrency 4). Fix: lower per-request timeout, return partials early.
- FLAGGED (LOW) — one corrupt track JSON row blanks the whole library
  snapshot (`getLibrary` per-row try/catch would fix it, as cache.ts already
  does); `/api/import/spotify` returns raw error messages to the client;
  free-text params (`q`, `title`, `artist`) lack length caps.
- Verified safe: yt-dlp runs via `execFile` with a fixed argv and
  regex-validated videoId (no injection); response shapes match the client
  stores; single-flight caching prevents stampedes; no secrets in server code.

## 5. Renderer / player (src/lib/player-engine.ts, src/stores/**, src/components/**)

- FIXED (HIGH) — **`enqueue`/`removeFromQueue` never updated the shuffle
  order array**: appended tracks were never played and an inserted one ended
  the session right after it played; removals left stale indices that
  replayed wrong tracks. Both now rebuild the order (shuffle: surgical
  insert/remove with orderPos correction; sequential: identity rebuild).
  Related and also FIXED: `playQueue`/`playFromQueue` set `orderPos = 0` on a
  non-shuffled identity order, so "play album from track 3 → next" jumped to
  track 1 — orderPos now points at the current track.
- FIXED (HIGH) — **permanent 400 ms re-render storm**: `syncFromEngine`
  unconditionally `set()` a new state object every engine tick, notifying 15+
  whole-store subscribers (every TrackRow, overlays) ~2.5×/s. Now it bails
  out when nothing visible changed.
- FIXED (HIGH) — **`ensureYT()` could hang forever** (the YT.Player promise
  settles only from `onReady`; a blocked embed never fires it → play click
  stuck with no failure, no skip). Now raced with a 12 s timeout so the
  failure policy takes over.
- FIXED (HIGH) — **Retry in the error banner destroyed the queue**
  (`playTrack` = 1-track queue). Retry now re-loads the failed entry in place
  (`playFromQueue`) when it is in the queue.
- FIXED (MED) — **radio auto-advance race**: a late `/api/radio` response
  yanked playback from a track the user had just started. The response now
  re-checks the current videoId before extending/advancing.
- FIXED (MED) — **stale warm-up target**: `engine.setNextTrack` only keyed on
  the current track; enqueue/extendQueue could change the successor without
  changing the current track. Now keyed on both.
- FIXED (MED) — shuffle toast announced the pre-toggle state ("Shuffle on"
  while turning it off) in PlayerBar and NowFull — reads state after the
  toggle.
- FIXED (LOW) — blob URL leaked when a local (downloaded) track errored;
  update-check fetch has a 10 s timeout (Settings could hang on "Checking…");
  `useUpdate`'s dead expression removed.
- FLAGGED (MED) — download has no stall timeout/cancel: a hung `/api/stream`
  body leaves the track permanently "busy" (fix: idle timer + AbortController
  + a cancel affordance).
- FLAGGED (MED) — SSR/hydration: module-scope `localStorage` reads and
  synchronous zustand-persist hydration can mismatch SSR output on launch
  (fix: `skipHydration` + explicit rehydrate in a mounted client component).
- FLAGGED (LOW) — non-player components (TrackRow, views, overlays) subscribe
  to the whole player store; narrow selectors would cut re-renders further.
  IndexedDB connections not closed on error paths; small unbounded session
  maps (prefetch `attempted`, lyrics/credits caches); toast dedupe.

## 6. CI / release

- FLAGGED (HIGH) — builds have **no test gate** (test.yml is independent of
  desktop.yml/desktop-tauri.yml) and use `npm install` instead of `npm ci`,
  floating `@tauri-apps/cli@latest`, no committed `Cargo.lock`. Fix: `needs:
  test`, `npm ci`, pin the CLI, commit the lockfile.
- FLAGGED (MED) — yt-dlp and the Node sidecar are downloaded at build time
  without checksum verification (pin exact versions + SHA-256).
- FLAGGED (LOW) — release scripts read the token from ad-hoc files; the
  `head_sha` filter on the runs API needs the full 40-char SHA (documented in
  PROJECT-NOTES after it bit us once).
